# Inspección offline de Codex CLI

La instalación examinada es `codex.exe`, ruta `C:\Users\Steeven\.vscode\extensions\openai.chatgpt-26.908.40401-win32-x64\bin\windows-x86_64\codex.exe`, versión `codex-cli 0.154.0-alpha.6.2`. Se consultaron solo `--version`, `--help`, `exec --help`, `sandbox --help` y `features list`; no se envió ninguna solicitud de modelo.

La sintaxis no interactiva documentada es `codex exec [PROMPT]`. El argumento `-` lee el prompt de stdin. `--json` envía eventos operacionales como JSONL a stdout, `--output-last-message` guarda el último mensaje del agente en un archivo y `--output-schema` acepta un archivo JSON Schema para la respuesta final. El wrapper pasa el prompt por stdin y captura por separado JSONL, stderr y mensaje final. Exige código de salida cero y un evento terminal `turn.completed` o `response.completed`; el nombre real del evento terminal no pudo confirmarse sin hacer una petición, por lo que el wrapper falla de forma cerrada si no aparece.

`--ephemeral` evita continuar una sesión persistida. Cada etapa se configura como solicitud independiente. `--model` permite seleccionar un modelo, pero no se fijó ninguno porque la tarea no escogió uno y `--help` no informa el modelo predeterminado. La metadata reporta versión y modelo solicitado. Solo un campo explícito de identidad servida, `server_model`, se aceptaría como modelo real; un campo genérico `model` no se reinterpreta. En la CLI local no pudo confirmarse que `server_model` se emita. No se documenta desde ayuda una tabla estable de códigos de salida; se preserva el código literal y cualquier valor distinto de cero es fallo de CLI/transporte.

Para reducir configuración heredada se preparó `--ignore-user-config` (la propia ayuda indica que la autenticación sigue usando `CODEX_HOME`) y `--ignore-rules`. No se usan `--add-dir`, `--approve-for-me`, `--dangerously-bypass-approvals-and-sandbox`, ni `--dangerously-bypass-hook-trust`. Se fijan `--sandbox read-only`, `--ask-for-approval never` y un cwd temporal nuevo por solicitud. El prompt y schema de salida se limitan a los registros congelados de XMODEL-011.

No hay perfiles de permisos definidos en el `config.toml` local. `codex sandbox --help` exige `--permission-profile`; el preset incorporado `:read-only` permitió ejecutar una prueba inocua desde `%TEMP%` y devolvió `outside_repo_file=True` al comprobar si podía leer el brief de XMODEL-010. También se repitió la comprobación con `-c windows.sandbox="unelevated"` y el archivo continuó siendo legible. Esto prueba que el aislamiento efectivamente disponible en esta CLI no oculta el repositorio. `features list` muestra `windows_sandbox_service` como “under development” e inactivo. El límite real verificado es que **el prompt transmitido** contiene solo registros inventariados de `model-visible/` y ningún output histórico; no existe todavía una garantía técnica de que herramientas internas de Codex no puedan descubrir otros archivos. La documentación oficial describe modos Windows `elevated` y `unelevated` con límites de permisos de filesystem, pero el modo adecuado requiere configuración del entorno y no quedó establecido aquí; la prueba local tiene prioridad para esta versión/configuración. Véase la [documentación oficial del sandbox Windows](https://learn.chatgpt.com/docs/windows/windows-sandbox) y la [guía de sandbox/aprobaciones](https://learn.chatgpt.com/docs/agent-approvals-security).

`--output-schema` proporciona una exigencia de serialización al modelo; no añade decisiones musicales. Stage 2 usa el schema genérico `{"type":"object"}`, que fuerza solo un objeto JSON, sin derivar propiedades musicales del YAML descriptivo. Los gates externos siguen siendo obligatorios.

El runner de XMODEL-011 ahora ejecuta ese preflight real antes de reservar el request ID y bloquea sin consumir un intento si alguna condición falla. La llamada a `codex exec` hereda como cwd el workspace externo. La autenticación sigue en el proceso Owner que invoca la CLI; las herramientas del agente bajo el token restringido no pueden enumerar o leer CODEX_HOME. La política ACL es reversible con `apply-filesystem-boundary.ps1 -Mode Remove`; no se modificaron bytes de XMODEL-010 ni payloads de XMODEL-011.
